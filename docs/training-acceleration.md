# 年度训练吞吐分析与加速

本文记录年度 `annual5m` 训练的吞吐瓶颈定位、根因与已验证的加速措施。结论面向 8×A100-SXM4-40GB
单节点，数据根为 `/data/heyuhang/processed`（网络文件系统）。所有数字均为本机实测，不是估算；
复现方法写在每节里。原始日志和一次性基准脚本不进入 Git。

## 1. 结论摘要

以 `configs/production/annual5m_v1.yaml` 出厂设置为基线，8 卡实测 **6.55 样本/秒**，
训练集 101,120 样本/轮（2020 + 2021 各 50,560），100 轮需 **17.9 天**。

定位结果：瓶颈既不是磁盘带宽，也不是 GPU 算力，而是 **GDAL 打开文件时对目录的 `readdir`**。
修复后 8 卡吞吐 **55.18 样本/秒**，100 轮 **2.12 天**，端到端 **8.43×**。

| 配置 | 样本/秒 | 小时/轮 | 天/100 轮 | 相对基线 |
|---|---:|---:|---:|---:|
| 基线 `bs1 nw2 ckpt=on`，无 GDAL 修复 | 6.55 | 4.29 | 17.87 | 1.00× |
| A 仅 GDAL 修复 `bs1 nw2 ckpt=on` | 36.09 | 0.78 | 3.24 | **5.51×** |
| B A + `num_workers=8` | 35.51 | 0.79 | 3.30 | 5.42× |
| C B + `batch_size=4` | 46.24 | 0.61 | 2.53 | 7.06× |
| D C + 关闭梯度检查点（推荐） | **55.18** | **0.51** | **2.12** | **8.43×** |

D 行 55.18 含启动预热；稳态（batch 1→25）为 63.5 样本/秒。两者都记录，避免用稳态数字夸大全程。

C、D 两行同时改了训练超参，已按 §3.6 做端到端对照：保持全局批量 32 不变时，改动对留出验证
loss 的影响小于纯随机种子造成的差异，已落到 `configs/production/annual5m_v1.yaml`。

## 2. 瓶颈定位过程

### 2.1 先排除两个常见嫌疑

裸文件系统并行读取（16/48 线程，`read_bytes`）达 1,172 / 1,879 MB/s、5,784 / 9,274 文件/秒，
而训练期实际只拉到约 29 MB/s；48 个 worker 进程各自只占 4% CPU。**带宽和 CPU 都不是瓶颈。**
（这批文件被先前的审计访问过，页缓存已热，故属带宽上界；但与 29 MB/s 差两个数量级，
结论不受影响。）

单卡算力天花板（真实 batch 预载内存后只计前反向）：

| 梯度检查点 | batch | 样本/秒/卡 | 前向 ms | 反向 ms | 优化器 ms | 峰值显存 |
|---|---:|---:|---:|---:|---:|---:|
| 开 | 1 | 6.66 | 50.1 | 95.2 | 4.7 | 2.60 GB |
| 开 | 2 | 7.74 | 85.7 | 170.0 | 2.7 | 5.00 GB |
| 开 | 4 | 8.60 | 145.5 | 316.7 | 2.7 | 9.93 GB |
| 关 | 1 | 8.46 | 49.6 | 66.2 | 2.4 | 4.84 GB |
| 关 | 2 | 9.67 | 81.1 | 123.1 | 2.6 | 9.62 GB |
| 关 | 4 | **10.53** | 144.9 | 232.3 | 2.7 | 19.38 GB |

（两次独立复跑差异 <1%。该探针用 fp16 autocast，而 A100 实跑走 bf16 且不挂 GradScaler，
因此这里是天花板的保守近似，不是逐位等价的运行时。）

基线每卡仅 0.82 样本/秒，**只用到算力的 12%**，88% 的时间在等数据。

### 2.2 对 `__getitem__` 分段插桩

单进程 60 个样本，每样本 23.4 个 observation（s2 11.33、s1 11.90、高分 0.17）、2.31 兆像素：

| 阶段 | 修复前 ms/样本 | 占比 | 修复后 ms/样本 |
|---|---:|---:|---:|
| `rasterio.open` 数据文件 | 415.61 | 42.2% | 40.44 |
| `rasterio.open` 掩膜文件 | 431.32 | 43.8% | 56.69 |
| `raster.read` 取值 | 64.17 | 6.5% | 44.85 |
| 掩膜文件读取 | 20.76 | 2.1% | 5.86 |
| 路径与几何解析 | 14.87 | 1.5% | 18.55 |
| 归一化 / 有限性 / 填充检查 | 26.59 | 2.7% | 24.50 |
| **`_read` 合计（60 样本）** | **59.10 s** | | **12.09 s** |

**86% 的时间花在打开文件上，真正解码只占 8.6%。**

### 2.3 根因

单文件计时：裸 `open()` + 读 4 KB 为 1.36 ms，`rasterio.open()` 仅读头就要 17.49 ms，
**12.9 倍开销全在 GDAL 的打开路径**（完整读取只再加 2.7 ms）。

原因是 GDAL 默认在打开文件时 `readdir` 所在目录以查找 sidecar（`.ovr`/`.aux.xml`/`.msk`）。
本数据集按 `source/年/月` 组织，**单目录约 123,000 个文件**：

```
123184 files  national_training_v1/lowres/s2/2020/08
120328 files  national_training_v1/lowres/s1/2020/05
```

每样本 23.4 个 observation × 2 个文件（数据 + 掩膜）= **46.8 次 open**，每次都在网络 FS 上
列举 12 万条目录项。这同时解释了为什么加 worker 无效——所有 worker 争用同一个元数据路径。

## 3. 已验证的加速措施

### 3.1 关闭 GDAL 目录探测（决定性，零风险）

```bash
export GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR
export GDAL_PAM_ENABLED=NO
```

`rasterio.open` 头部读取 17.49 ms → **2.01 ms**。取值必须是 `EMPTY_DIR`：

| 取值 | ms/文件 |
|---|---:|
| 未设置 | 17.76 |
| `TRUE` | 4.03 |
| `EMPTY_DIR` | **1.90** |

`GDAL_PAM_ENABLED=NO` 单独只有 ~10% 收益，但可避免写出 `.aux.xml` 污染数据目录，建议一并设置。

DataLoader 扩展性（单进程组，`batch_size=1`）对照：

| num_workers | 基线 样本/秒 | 修复后 样本/秒 | 加速 |
|---:|---:|---:|---:|
| 0 | 0.96 | 4.04 | 4.2× |
| 8 | 6.34 | 35.83 | 5.7× |
| 16 | 8.52 | 73.57 | 8.6× |
| 32 | **10.00** | **169.60** | **17.0×** |

基线在 ~10 样本/秒饱和（元数据争用），修复后近似线性扩展。该扫描重复遍历 3,000 条记录，
高 worker 档位受页缓存加成，趋势可靠但绝对值偏乐观。

**已落地。** 原先这个开关只出现在 `xuannv data validate` 的审计路径
（`data/annual_dataset.py` 的 `check_manifest`），训练路径从未设置，且用的是较弱的 `TRUE`。
现已改为在 `data/annual_dataset.py` 模块导入处 `os.environ.setdefault(...)`，训练、导出、
审计三条路径统一生效，不依赖启动脚本传环境变量；显式设置的环境变量仍然优先。

进程内设置能否被 GDAL 读到是这个改动成立的前提，已单独验证：在启动时未设该变量的进程里，
仅导入本模块即可让同一目录（123,184 个文件）的 `rasterio.open` 从 19.4 ms 降到 4.1 ms
（两次复跑 19.75/19.03 → 4.08/4.14）。`os.environ.__setitem__` 会调用 `putenv`，
GDAL 的 `CPLGetConfigOption` 因此可见。

端到端复核：在启动时未设任何 GDAL 变量的进程中，真实 `AnnualObservationDataset` +
`num_workers=8` 的吞吐为 **36.65 样本/秒**，与显式导出环境变量的 35.83 一致，
而未修复的基线是 6.34。改动无需启动脚本配合即可生效。

### 3.2 关闭梯度检查点

40 GB 卡上无需省显存：检查点让反向慢 44%（95.2 → 66.2 ms @ bs1），只省 2.24 GB。
`batch_size=4` 且关闭后峰值 19.38 GB，仍有一半余量。实测贡献 46.24 → 55.18 样本/秒（+19%）。

### 3.3 提高 batch size

`batch_size=1 → 4` 贡献 35.51 → 46.24 样本/秒（+30%）。注意 `num_workers` 单独调整
（A→B）**无收益甚至略负**：GDAL 修复后瓶颈已转回算力，加 worker 只增加进程开销。
这一点与修复前的直觉相反，必须先修 GDAL 再谈 worker。

### 3.4 推荐运行配置

GDAL 环境变量已内建（§3.1），无需在启动脚本里导出：

```bash
scripts/cuda/launch.sh configs/production/annual5m_v1.yaml --output /path/out/checkpoint.pt
```

下面四项**已经落到 `configs/production/annual5m_v1.yaml`**，无需再改：

```yaml
training:
  gradient_accumulation_steps: 1  # 原 4
  gradient_checkpointing: false   # 原 true
data:
  batch_size: 4                   # 原 1
  num_workers: 8                  # 原 2
```

`gradient_accumulation_steps` 必须与 `batch_size` 反向同步：全局批量
= 8 × `batch_size` × `gradient_accumulation_steps`，`4×1` 与 `1×4` 都是 32。
**保持全局批量不变是这套改动不需要重调学习率、warmup 和 `uniformity` 负样本数的前提**——
跨卡聚合后的负样本数由全局批量决定，仍是 32。
等价性已按 §3.6 实验确认；配置摘要变化会使旧 checkpoint 无法恢复。

### 3.6 超参等价性实验（已确认，可落生产配置）

§3.2 与 §3.3 改的是训练超参而不只是性能开关，因此单独做了一组对照实验。

**梯度检查点：数值上免费。** 同一批真实数据，开/关检查点的 loss 差 5.782e-05、梯度相对差
1.234e-03；而开/开重复两次得到的是**完全相同**的 5.782e-05 / 1.234e-03。差异等于非确定性本底，
不是算法变化。

**batch size：确实改变目标函数，但影响小于种子噪声。** `reconstruction_loss` 用
**全局** masked 求和除以**全局** masked 计数，所以一个 micro-batch 内每个*有效像元*等权；
而 `bs=1` + 累积是每个*样本*等权。300 个真实样本的有效像元数 CV 为 0.214，
p95/p5 = 2.0×，最坏样本间相差 13.09×——机制真实存在。另外留出请求
（`reconstruction_requests`）的抽取本身也是随机的，bs=1 与 bs=4 不可能逐位对齐，
所以只能做端到端对照，不能追求梯度逐位相等。

三次 8 卡短跑，样本预算完全相同（32,768 样本、1,024 个 optimizer step、4 轮、
`--max-records 4096`）：

| 运行 | 配置 | 墙钟 | 样本/秒 | 每卡峰值显存 | 非有限梯度步 |
|---|---|---:|---:|---:|---:|
| A | `accum4 bs1 ckpt=on` seed 42 | 874.0 s | 37.49 | 3.39 GB | 0 |
| A2 | 同 A，仅 seed 改为 4242 | 877.9 s | 37.33 | 3.39 GB | 0 |
| B | `accum1 bs4 ckpt=off` seed 42 | **551.5 s** | **59.42** | 22.56 GB | 0 |

B 比 A 快 **1.585×**；A 与 A2 的吞吐差 0.4%，说明计时本身可复现。

三个 checkpoint 在**同一组** 512 个留出验证 batch 上评测（2020/2021 验证 manifest 各 256 个，
batch 固定为 1、掩码用固定种子预先生成一次后复用，因此三个模型看到逐位相同的输入与留出区域）。
A2 是噪声本底：它与 A 只差随机种子，任何超出这个差距的变化才算信号。

| 配对对比（n=512） | Δtotal | Δrecon | Δhighres_recon |
|---|---:|---:|---:|
| B − A（待确认的改动） | +0.145% | +0.072% | +0.717% |
| A2 − A（仅换种子，噪声本底） | −0.553% | +0.167% | −6.19% |

**三个分量上，待确认改动的效应量都小于纯种子噪声**（total 小 3.8×、highres_recon 小 8.6×、
recon 小 2.3×）。结论：在该预算下 `accum4 bs1 ckpt=on → accum1 bs4 ckpt=off` 与基线不可区分，
且快 1.585×，可以落到生产配置。

限制，必须一并记录：4 轮、32,768 样本的短跑只能排除明显劣化，不能排除 100 轮长训中的缓慢分化；
噪声本底只取了一个种子对，是单次采样而非分布。正式长训仍应按 §3.4 起跑后核对前若干轮的
loss 轨迹与 `nonfinite_gradient_steps`。

### 3.5 `relative_file()` 只解析一次数据根（收益有限，已落地）

`relative_file()` 原先对结果路径和数据根**各做一次** `.resolve()`。数据根在进程内是常量，
现用 `lru_cache` 只解析一次（`data_process/annual_quality.py`）。

这一项的实际收益远小于最初的估计，记录在此以免后人重复踩坑。最初测得
"552 µs → 52.2 µs，10.6×"，**该结论是错的**：两个变体先后跑在同一批路径上，
后跑的那个白拿了前一个预热的 dentry 缓存。改用互不相交的路径集重测：

| | 冷缓存 µs/call | 热缓存 µs/call |
|---|---:|---:|
| 原实现（两次 resolve） | 720.6 | 64.1 |
| 现实现（缓存数据根） | 593.5 | 48.7 |
| 比值 | 1.21× | 1.32× |

真正的开销是**叶子路径**在网络 FS 上的冷查找（720 µs vs 热态 64 µs），而
`root.resolve()` 只占约 15 µs/call。折合每样本 46.8 次调用约省 0.7 ms，相对
§3.1 的数十毫秒可以忽略。保留该改动只因为它是严格的减法，不改变任何语义。

安全语义经用例核验完全不变：结果路径仍逐次完整 `resolve()`，
绝对路径、`..`、URL、反斜杠、**指向根外的符号链接叶子文件**和符号链接目录全部照旧拒绝。

> 曾评估过更激进的变体：再记忆化父目录的解析结果（500 条路径只涉及 27 个目录），
> 可降到 10.9 µs。**已否决**——父目录在根内不等价于叶子文件在根内，
> 符号链接指向根外的文件会漏检，而上表显示它换来的收益本就微不足道。

## 4. 尚未实施的候选

按预期收益排序，均已测量但未改代码：

1. **消除独立掩膜文件**：掩膜单独一个文件使 open 次数翻倍，修复后仍占 `_read` 的 28.1%。
   若在物化阶段把掩膜并为数据文件的附加波段或 GDAL 内部掩膜，可再省约四分之一。
   属于数据格式变更，需重新物化并重算校验和。
2. **预打包每 patch 的年度堆栈**（zarr / sharded）：把 46.8 次 open 降到 1 次。
   收益最大但工程量也最大，且需要约 1.8 TB 额外空间与全量重跑。
   在 §3.1 已经把吞吐拉到算力天花板 65%（55.18 / 84.2 样本/秒）的前提下，**优先级应降低**。
3. `torchrun` 默认把 `OMP_NUM_THREADS` 设为 1。当前 worker 并非 CPU 受限，调高无意义，
   但若将来改用 CPU 密集的重采样路径需重新评估。

## 5. 复现与注意事项

- 解释器固定用与本仓同装的那个；系统 `python` 缺少 torch 与 rasterio，结果不可信。
- 启动器只能用 `scripts/cuda/launch.sh`。`training/cli.py` 没有 `__main__` 守卫，
  直接 `torchrun -m xuannv_embedding.training.cli` 会静默退出 0 且不产出任何东西。
- 吞吐测量必须在集群空闲时进行；跨节点共享 FS 在并发 DDP 下抖动可达 2–3 倍。
- **页缓存会伪造出加速比。** §3.5 记录的错误结论就是这么来的：先后测两个变体时，
  后者复用了前者预热的 dentry 缓存，凭空多出近 10×。凡是涉及路径解析或文件打开的 A/B，
  必须让每个变体跑在**互不相交且同样冷**的路径集上，并同时报告冷/热两组数字。
- **超参 A/B 必须带种子对照。** 只比"改动前 vs 改动后"两个 checkpoint 无法判断差异是不是
  信号：§3.6 里仅更换随机种子就让留出 `highres_recon` 变化 6.19%，是待测改动的 8.6 倍。
  评测 batch 也必须预先生成一次后复用，让所有 checkpoint 看到逐位相同的输入和留出区域。
- 所有加速项均不改变数值结果：A–D 四次消融的 `nonfinite_gradient_steps` 均为 0，
  loss 量级一致。§3.4 的超参变更按设计会改变训练轨迹，其影响量级见 §3.6。
