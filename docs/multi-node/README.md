# 多节点训练指南

面向 24 卡（3 节点 × 8 卡）及以上规模的 CUDA 训练。内容是分层验收流程、故障速查与
ACP 迁移要求，均由实机联调沉淀而来，换集群时可直接复用。

单机多卡、导出与下游评测见 `docs/training-export-downstream.md`；本目录只讲跨节点。

## 当前方案

两个阶段，分工明确：

| 阶段 | 环境 | 网络 | 用途 |
| --- | --- | --- | --- |
| 调试 | 自有 3 节点 24 卡 | TCP（`NCCL_NET=Socket`） | 排训练侧的坑：DDP、梯度累积、checkpoint 合同 |
| 正式训练 | 大装置 ACP | RDMA（IB / RoCE v2） | 全量训练 |

这样切分的原因是：调试阶段的容器**拿不到 RDMA**（见 `acp-migration.md`），而训练侧的问题
与网络后端无关——用 TCP 一样能全部暴露。等 ACP 环境到位时，只剩环境差异需要验证。

## 核心原则：逐层收敛，不要直接跑训练

跨节点训练失败时，可能原因横跨网络、解释器、驱动、训练代码四类，直接从最上层排查会
非常低效。正确做法是自底向上逐层验证，每层都有独立的、可单独运行的检查手段：

```
L0  单卡                    →  环境本身可用
L1  单节点多卡              →  卡间通信（NVLink / P2P）
L2  跨节点 rendezvous       →  端口互通、地址正确
L3  跨节点 NCCL 集合通信    →  网络后端可用（scripts/cuda/check_24card.sh）
L4  跨节点 synthetic 训练   →  训练代码在多卡下正确
L5  跨节点真实数据训练      →  数据管线
```

第 3 层的自检脚本不加载模型也不读数据，是把「网络问题」与「训练侧问题」分开的关键：
它通过而训练失败，问题一定在训练侧；它就失败，不必去看训练代码。
